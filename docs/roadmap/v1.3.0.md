## 1. Goals and ground rules

**Goals of 1.3.0**

- A new board finds the best of the test environments you already have, mostly for the biggest useful batch (E1).
- The two solder jigs become one product: the same size, slotting into each other, optionally hinged and latched,
  so the turn-over step cannot shift anything (E2, E4).
- You can *see* how snug every part sits in its jig before printing (E3).
- Jigs can be printed in several materials, chosen per part for what that part needs (flexible for parts that vary
  in size, heat resistant, sturdy, ESD safe, cushioning, ...). The toolkit suggests these needs, you decide, and it
  makes a jig whose structure holds (E5).
- Every build states what it costs, and a test environment can be downgraded to a budget with the losses spelled
  out (E6).

**Ground rules (unchanged from AGENTS.md, they bind every item)**

- Standard library only in `pcbtestkit/`, `plugin/` and `tools/`; Python 3.9 compatible; relative imports in the
  plugin. New file formats (3MF, for example) are written with `zipfile` and `xml.etree`.
- New knowledge is **data, not code**, like the class systems: materials, printers, package tolerances, price
  tables and need rules are JSON files with a validator and test vectors.
- Tools never raise, writes go through `Workspace.apply` (dry run, confirm, audit, undo), and tool descriptions stay
  one or two sentences.
- Pages go through `htmlkit`: everything escaped, nothing loaded from the network, no new scripts (static SVG and
  CSS only; the one hashed table script stays the only script).
- No absolute paths or personal data in any output.
- **Old projects build exactly as before** unless they opt in, or unless a new default is proven to never make a
  jig worse (each epic says which defaults change). `pcbtestkit.json` gets a `schema` minor bump with a migration
  that only adds keys.

**Who it is for (context only).** The request explains the audience: people and companies with many different
products, each made in modest numbers, and smaller companies or production departments without the capital for a
production line per product. That is why cost (E6) and reuse of existing testers (E1) matter so much. The request
says explicitly that this context must not change the toolkit's code or function, so it is recorded here only.

## E1 Best test environment for a new board

**Problem.** Today a board is made for one test environment: its own `environment.path`, else the one remembered
with `environment use` (`settings.json`). With several environments built (a lab per site, a cheap one and a big
one, last year's and this year's), nobody tells you which one suits a new board best, and the batch size you get
depends on which one you happened to pick.

**Goal.** Before a board run, rank every known test environment and station for this board, mainly by the batch it
allows, and explain the ranking. Pick the best automatically when asked to; otherwise suggest.

### F1.1 A registry of known test environments

- `settings.json` gains `environments`: a list of `{path, name, id, added, last_used, fingerprint}`. `id` is a
  stable id written into `environment.json` at build time (a UUID, not derived from the path). `fingerprint` is the
  hash of the station boards' `board_sha` values, so the registry notices a station board edited in KiCad.
- The existing single remembered environment becomes the registry's **default** entry; old `settings.json` files
  migrate on first read (the remembered path becomes the only entry, marked default).
- Commands (CLI; the same through MCP and the KiCad dialog):
  - `pcbtestkit environment register DIR [--name NAME]`: add a built environment or a single station board.
  - `pcbtestkit environment list`: name, path (relative to home when possible), stations, boards, last used,
    health (see A8).
  - `pcbtestkit environment use DIR`: as today, and it also makes the entry the default.
  - `pcbtestkit environment forget DIR|NAME`.
  - `pcbtestkit environment discover DIR...`: find `environment.json` files under folders and offer to register
    them (never registers silently).
- An environment build or add registers its result automatically (opt out with `--no-register`).
- A registry entry whose folder is gone stays listed as *missing* until forgotten; it is never deleted silently.

### F1.2 Matching a board against every environment

For one board, for every registered environment and every station in it:

1. **Fast estimate (milliseconds per station).** Profile the board once (`environment.profile_board`, cached by
   `profile_key`), then `environment.estimate(profile, station_model, spec)` gives the batch, what limits it
   (inputs, supplies, buses, plate, programmers, max batch) and the blocker text when it does not fit.
2. **Exact check (seconds, top candidates only).** For the best *K* candidates (default 3, `--exact N`) run
   `station.plan_board` with the station's real facility: real nest entry, real fixture layout on the plate.
   The exact result replaces the estimate in the ranking.
3. **Inventory.** An environment may record what it owns (F1.5): programmers per interface, spare fixture plates,
   pogo pin stock. A batch of 8 programmed over SWD on an environment with 4 SWD probes is a batch of 4 unless you
   accept buying probes (shown as a cost, E6).

**Score.** One number per candidate for sorting, with every part shown:

| Objective (`--objective`) | Primary | Then |
|---|---|---|
| `batch` (default) | boards per load | time per board, new hardware cost, station load |
| `throughput` | boards per hour (timing.py batch flow) | batch, cost |
| `cost` | cost per tested board over the planned volume (E6) | batch, time |
| `coverage` | share of nets tested (more analog inputs, more probes) | batch |
| `reuse` | fewest new parts (no new programmers, plates, pins) | batch |

**The batch sweet spot.** The largest batch is not always the best: `timing.test_times` gives time per board for
every batch size; fixture sites and programmers cost money; a jig set must fit the printer bed (`batch.bed_mm`).
The match reports, per candidate, the largest batch, the batch with the shortest time per board, and (when a
production volume is set, `production.volume`) the batch with the lowest cost per tested board. The default pick is
the largest batch unless the sweet spot saves more than `environment.sweet_spot_margin` (default 10 %) per board.

**Station load (optional).** If a station already serves many board types, a new type adds fixture swaps. With
`--balance` the score includes the swaps per shift from the board's planned volume.

### F1.3 Choosing automatically

- `environment.path: "auto"` in `pcbtestkit.json` (and `--environment auto` on the CLI) picks the best match at
  every run. `"auto:throughput"` etc. picks by another objective. The choice is written into the spec
  (`environment.chosen`: id, name, station, batch, score, runner-up) so a rerun with the same inputs makes the same
  choice; ties break by registry order, then name.
- If nothing fits: the run goes on without an environment (the board's own fixture, as today) and the guide shows,
  per environment, the cheapest change that would take the board (`upgrades.plan_goal` with "this board must fit").
- If the choice changes between runs (a new environment registered, a station edited), the guide says what changed
  and why, and the fixture is rebuilt for the new station.

### F1.4 Where you see it

- **Guide and report:** a "Where to test it" card under the header: the chosen environment and station, batch, what
  limits it, time per board, and a small table of the other candidates with the reason each lost. One line per
  environment that cannot take the board, with its blocker.
- **CLI:** `pcbtestkit match BOARD [--objective batch] [--exact 3] [--json]` prints the table without building.
- **MCP:** `match_test_environments` (R): compact rows `[env, station, batch, limit, s_per_board, new_cost, score]`
  plus the chosen one; `set_test_environment` accepts `path: "auto"`.
- **KiCad dialog:** the environment box becomes a dropdown of registered environments, sorted by match, each shown
  as "Lab A / station-1: 8 per load (supplies)"; "Best match" is the first entry.
- **Several boards in one run** (the many-boards dialog, a station run): each board is matched on its own;
  `--same-environment` keeps them all on the environment that is best for the set (highest total score).

### F1.5 Environment inventory (optional)

`environment.json` may hold `inventory`: `{programmers: {swd: 4, isp: 2}, fixture_plates: 6, pogo_pins: {P75: 400}}`,
edited with `pcbtestkit environment inventory DIR --set swd=4`. Matching uses it for real limits and E6 for what
must be bought. Without an inventory nothing is limited by it (as today).

### F1.6 Edge cases

- Environments built by an older version: profiles are made again once (profile keys include the version that
  matters); stations are read from their KiCad boards as today (edits included).
- An environment on a network share that is slow or offline: matching has a per-environment time limit and marks
  it *unreachable* instead of hanging.
- A board that fits a station only with its other side probed (`probe_side`): reported, with the side.
- Different fab class systems per environment do not matter here (the board's own class decisions stay).

### Acceptance (E1)

- With three synthetic environments (tests build them from `examples/make_collection.py` subsets), a board that
  fits two of them gets the larger batch by default and the faster one with `--objective throughput`.
- `environment.path: "auto"` gives the same choice on two runs, and the spec records it.
- A missing environment folder never breaks a run: it is skipped with a note.
- Matching 1 board against 10 environments with 3 stations each takes under 5 s with `--exact 3` (excluding the
  first profile).

## E2 Placement and holding jigs of one size that slot together

**Problem.** The placement jig and the holding jig have different outer sizes: the holding jig's frame is
`jig.rim_mm` (3 mm) plus `edge_clearance_mm` around the board, the placement jig's is `jig.placement_border_mm`
(6 mm) plus its stops. That works, but the pair looks unfinished, does not register against itself (only through
the posts in the board's mounting holes, when there are any, and the stops), and cannot be stored as one block.

**Goal.** Both jigs share one outer outline and one datum, and slot into each other, *without* any loss of
function: pockets, wells, stops, posts, finger notches and every clearance stay exactly as they are.

### F2.1 One outline

- The common outline is the union of both jigs' current outlines, grown to the larger border on every side, with
  the same corner radius. Both jigs are built on the same grid (`resolution_mm`) with the same origin, so a batch
  (`tile_grid`) tiles both identically.
- The extra frame is solid to the jig's floor where it is narrower than `jig.min_frame_mm` (default 4 mm), else a
  shell with ribs (`jig.frame_style: solid|ribbed`) so the material and print time grow as little as possible.
  E6 reports the extra grams.
- If the common outline no longer fits the printer bed (`batch.bed_mm`), the jig set holds fewer boards (as today
  for a batch) and the guide says so; `jig.pair: "separate"` keeps today's sizes.

### F2.2 Registration (slotting together)

Choose with `jig.registration` (default `lip+pins`):

| Value | What it is | When |
|---|---|---|
| `lip` | the holding jig's frame has a skirt that slides over the placement jig's frame like a lid on a box; inner chamfer `jig.lip_chamfer_mm` (0.8) as a lead-in | every board |
| `pins` | two tapered pins on the placement jig, two sockets in the holding jig, at diagonal corners: one round socket, one slot along the diagonal so the pair never binds (exactly constrained) | every board |
| `lip+pins` | both (default): the lip finds the position, the pins fix it | default |
| `posts` | only the posts through the board's mounting holes (today) | `jig.pair: separate` |

Parameters: `jig.mate_clearance_mm` (0.25, all sliding fits; calibrate with A1), `jig.lip_height_mm` (auto: at
most the stop height so the placement jig still lifts straight off), `jig.pin_diameter_mm` (4), `jig.pin_taper_deg`
(5). The lip and pins stay clear of the stops (whose notches move to the lip), the finger notches (kept on both
jigs, offset so each jig can be gripped on its own) and the posts.

### F2.3 Checks

- `jigfit.fit_check` checks the pair closed: lip and pins never touch a part, lead or stop; the holding jig still
  lands on the parts exactly as before (the same pocket floor heights).
- `stack_collisions` includes the lip.
- The pair also stacks closed for storage; for a batch the pins sit in the outer frame only.

### F2.4 Video and guide

The cover shot shows the pins finding their sockets and the lip sliding over the frame; the unload shot shows the
placement jig lifting straight off. The guide's jig section gains a one-line explanation and a close-up render.

**Default.** `jig.pair: "matched"` becomes the default when the matched pair fits the printer bed with the same
number of boards; otherwise `separate` with a note. The paste-print nest keeps its own size (it has a different
job) but gets the same outline when `jig.paste_nest_matched: true`.

### Acceptance (E2)

- For the sample board, the published demos and 20 generated boards: both jigs have identical outlines (within one
  grid cell), the fit check passes, and every pocket floor height is unchanged against 1.2.0 (golden comparison).
- The pins never land on a part (test with a part in each corner).
- A printed pair (manual test, A1 coupon first) slides together without force and does not rock.

## E3 Clay fit visualiser in the jig videos and pages

**Problem.** The fit check proves that every part clears its pocket, but nobody can see how snug the fit is: a
pocket 0.15 mm from a part and one 1.2 mm from it look the same in a render.

**Goal.** Show the gap between each jig and the board as if a blanket of modelling clay had been pressed between
them: on top of the parts for the holding jig, under the board for the placement jig. Where the fit is snug the
clay is squeezed thin, where it is loose the clay stays thick, and the colour says how thick.

### F3.1 The gap field

On the jig grid (`resolution_mm`), with the jig closed in its working position:

- `J(x, y)`: the jig's surface that faces the board (the holding jig's pocket floors and walls seen from below; the
  placement jig's top surface, wells and rests seen from above).
- `C(x, y)`: the content surface: the parts' real envelopes (`parts3d`, the same shapes the fit check uses), the PCB,
  leads.
- `G = J - C` (holding jig) or `C - J` (placement jig). `G >= 0` everywhere after a passing fit check; `G < 0` is
  interference and is drawn in a warning colour (it should never reach a video).
- Side walls: the lateral gap per pocket wall (part outline to pocket wall) comes from the same cells and is
  shown on the clay's edges.

### F3.2 Squeezing the clay

- The clay starts as a slab of thickness `T0` (default 2 mm, `video.clay_mm`) lying on the content surface.
- When the jig closes, the clay at each cell becomes `min(T0, G)` thick. The volume pushed out where `G < T0`
  flows to neighbouring cells with room (`G > current thickness`), by an iterative relaxation on the grid, until it
  is absorbed or reaches the frame, where it curls out over the edge as visible excess. That is cheap (a few passes
  over the grid) and looks like real clay.
- **Colour bands** by final thickness, i.e. by local gap: `jig.snug_bands_mm` (default `[0.2, 0.5, 1.0]`) gives
  four bands, for example deep green (snug, up to 0.2 mm), green (to 0.5), amber (to 1.0), red (looser), and a
  warning magenta for interference. Colour-blind safe palette, the same in pages and video.
- **Intentional room is marked, not judged.** Lead wells, heat-insert room (`heat_insert_mm`), `jig.room`,
  relief pockets and E5 soft liners are known zones in the jig grid; they are drawn hatched in a neutral colour
  with a legend ("room for leads", "room for a heat insert") so nobody mistakes them for a bad fit.

### F3.3 New shots

Two-jig workflow (each about 6 s; names get the side for a bottom-side set like every jig shot):

| Shot | What happens |
|---|---|
| `clay_hold` | the clay blanket settles over the parts in the placement jig, the holding jig comes down and squeezes it (excess curls out at the frame), holds, then lifts: the imprint stays on the parts, coloured by gap, while the camera turns once around it |
| `clay_place` | the clay lies on the placement jig; the PCB with its parts comes down and squeezes it; lifts again to show the imprint under the board |
| `clay_section` (optional) | a cut through the closed stack along the tightest part, so the clay thickness is seen in profile |

The shots sit after `cover` and before `flip` (and `clay_place` after `place2`). `video.clay: auto | on | off`
(auto: on when any part sits closer than the first band or looser than the last). The single-jig workflow gets
`clay_hold` only.

**Rendering.** Every frame stays an ordinary KiCad scene. The clay is written as VRML per frame like the nest and
clamp models (`anim_clamp_*.wrl`), meshed with the existing heightmap mesher (top and bottom surface, side walls),
one shape per colour band with its own material, so it does not depend on per-vertex colours in KiCad's VRML
reader. Frame count stays within the quality preset's budget (fewer frames for the imprint turn at `basic`).

### F3.4 In the guide and report (static, no script)

- A top view per jig: the clay imprint as an image (a PNG rendered from the gap field, the same colours), with the
  legend.
- A "How snug every part sits" table: part, smallest and largest gap, share of its contact area in each band,
  verdict ("snug", "loose: consider a flexible liner (E5)", "intentional room"), sortable.
- `<board>-jig-fit.json`: the same numbers per part and per jig, for agents (`read_output` with a pointer).
- Suggestions link to E5: a part that is loose all round with a known size tolerance gets the suggestion of a
  flexible liner; a part with interference shows the finding.

### Acceptance (E3)

- The gap field of a synthetic pocket with known clearances (0.15 / 0.5 / 1.2 mm on three sides) gives exactly those
  bands.
- Clay volume is conserved within 2 % (squeezed volume = volume shown as excess plus pooled).
- Videos with `video.clay: off` are frame-for-frame identical to 1.2.0.

## E4 Hinged jig pair with a briefcase latch

**Problem.** Turning the stack over (the `flip` step) relies on the operator holding two loose jigs together. A
slip shifts the parts before they are soldered.

**Goal.** The two jigs become one folding piece: a hinge on one side, a latch on the other that locks them like a
briefcase. Folding is the `cover` step, latching makes the stack rigid for `flip`, and unlatching and swinging the
placement jig away is `unload`.

### F4.1 Hinge types (`jig.hinge`)

| Value | Description | Needs |
|---|---|---|
| `none` | as today | |
| `pin` (default when hinged) | knuckles printed on both jigs, joined by a pin: a 3 mm steel rod, a 1.75 mm filament piece or a printed pin | a pin (listed in the guide's parts) |
| `print_in_place` | knuckles printed already joined (captive cone pin, support-free), the pair printed unfolded as one part | bed big enough for both side by side; clearance calibrated (A1) |
| `lift_off` | open hook knuckles: the placement jig can be lifted off when unfolded flat, and goes back on the same hooks | nothing |
| `slotted` | the pin runs in a short vertical slot, so the last part of the closing motion is straight down (and the first part of opening is straight up) | chosen automatically when a plain hinge would sweep through a part (F4.3) |
| `living` | a strip of flexible material joins the jigs (E5, multi-material printers only) | a flexible material |

Geometry: the axis lies along the chosen edge (`jig.hinge_edge: auto|north|south|east|west`; auto = the longest edge
with the fewest tall parts nearby and no finger notch) at the **mating plane** of the matched pair (E2), just
outside the frame, so the jigs close face to face with no gap. Knuckle count from the edge length (each knuckle at
least 8 mm long, `jig.hinge_clearance_mm` 0.35 between knuckles). Unfolded, both jigs lie face up side by side,
exactly the way they are printed for `print_in_place` (which is why E2's equal frame heights matter).

### F4.2 Latches (`jig.latch`)

| Value | Description |
|---|---|
| `briefcase` (default when hinged) | an over-centre toggle latch on the edge opposite the hinge: a printed lever on the holding jig, a hook on the placement jig, pinned like the hinge. Two latches when the edge is longer than `jig.latch_every_mm` (120) |
| `snap` | a cantilever snap hook with a release tab, sized for a target holding force (`jig.latch_force_n`, 15 N) from the material's modulus |
| `magnet` | pockets for disc magnets (`jig.magnet: "6x3"`), press fit with a glue gap; never within 5 mm of a part (the guide warns for parts with ferrous leads) |
| `screw` | thumb-screw bosses for heavy boards |
| `none` | |

The latch lever, hook and their swing never come near a part, a lead or the solder side; on the solder side the
frame stays flat so the iron can reach every joint.

### F4.3 Motion checks (swept volumes)

- **Folding (cover):** the holding jig is rotated about the axis in steps (default 2 degrees) from open to closed;
  at each step its solid (from the jig grid) is checked against the parts' envelopes and the PCB. A collision near
  the hinge (tall parts there) makes the toolkit switch to `slotted` (slot length = deepest pocket wall near the
  axis plus clearance), then try another edge, and report the choice.
- **Opening after the flip (unload):** the placement jig swings away from the leads that now point up; the same
  sweep is checked against the leads (their length is limited by `placement_clearance_mm`). A collision gives
  `slotted` or `lift_off`, or a note to trim the leads first.
- **Latch swing:** the lever's path is swept the same way.
- Results go into the fit check (`jigfit`) and the fit-check files.

### F4.4 Workflow, guide and video

- The six steps become: print the pair (one part or two plus a pin), place the PCB, fit the parts, **fold** the
  holding jig over, **latch**, turn over, **unlatch and swing** the placement jig open, solder, unlatch and lift
  the board out.
- Video shots: `fold` (replaces `cover` when hinged), `latch` (a close-up of the lever going over centre),
  `flip`, `swing` (replaces `unload`). With E3, the clay shot runs with the hinged motion.
- `timing.assembly_times` gets the handling times for fold, latch and swing.

### Acceptance (E4)

- For every published example, the hinged pair passes the fold and swing sweeps, or the toolkit picks `slotted` /
  another edge and says why.
- With `jig.hinge: none` the outputs are identical to E2's.
- `print_in_place` is refused with a clear reason when the unfolded pair does not fit the bed.

## E5 Multi-material jigs and per-part needs

**Problem.** One rigid material is a compromise: parts vary in size (an electrolytic's diameter, a connector's
ground pin that sticks out further than its 3D model), some parts get hot, some are fragile, some are sensitive to
static. A rigid pocket must be loose enough for the biggest part, so the smallest one rattles.

**Goal.** Let each part ask for what it needs: a flexible liner that forms around it, a heat-resistant zone, a
stiffer frame, an ESD-safe contact, and many more. The toolkit suggests the needs (it detects most of them), you
accept, change or switch them off per part, and it builds jigs that combine several materials into one strong,
printable piece. Printers with one material get the best fallback (separate liners, cast silicone, cut inserts).

This epic is the largest; it is split into F5.1 to F5.12.

### F5.1 Materials library (data)

`pcbtestkit/materials/*.json`, one file per material, validated by `pcbtestkit materials validate` with test
vectors, like the class systems. Fields:

| Field | Example (TPU 95A) | Used for |
|---|---|---|
| `id`, `name`, `family` | `tpu-95a`, "TPU 95A", `tpu` | |
| `kind` | `flexible` (rigid, flexible, elastomer_cast, sheet) | |
| `shore` | `95A` | softness of liners |
| `modulus_mpa`, `elongation_pct`, `tensile_mpa` | 26, 580, 40 | snap and latch sizing, liner stiffness |
| `hdt_c` (0.45 MPa), `max_service_c` | 70, 80 | heat needs |
| `density_g_cm3` | 1.21 | grams, cost |
| `price_per_kg` | 30 (rough, overridable) | E6 |
| `print`: nozzle and bed temperature, enclosure, hardened nozzle, max volumetric flow | 225 / 50 / no / no / 3.5 | printer compatibility, time |
| `surface_resistivity_ohm` | null (ESD grades have 1e6..1e9) | ESD needs |
| `thermal_conductivity_w_mk` | 0.2 | heat paths |
| `chemical`: flux, IPA | good, good | chemical needs |
| `bonds_with`: per material id, `good / fair / poor` | PLA good, PETG good, ABS fair | interlock rules (F5.7) |
| `verified` | date the properties were checked | |

Initial set: PLA, PLA+, PETG, PETG-CF, ABS, ASA, PC, PA12, PA-CF, PC-ABS, PEI (high end), ESD-PETG, ESD-ABS, TPU
95A, TPU 90A, TPU 85A, TPE 70A, PEBA, flexible PLA; non-printed: cast silicone (Shore 20A..60A), PTFE sheet,
FR-4 sheet, silicone sheet, cork, EVA foam. Users add their own file or inline material in `pcbtestkit.json`.

### F5.2 Printer profiles (data)

`pcbtestkit/printers/*.json` and `printer` in `pcbtestkit.json` (and in `settings.json` for every project):
`bed_mm` (replaces `batch.bed_mm`, which stays as an alias), `tools` (number of materials in one print),
`tool_type` (`single`, `idex`, `toolchanger`, `mmu_single_nozzle`), `nozzle_mm`, `max_nozzle_c`, `enclosed`,
`hardened`, `purge_mm3` per change (single-nozzle MMUs), `inventory` (materials on hand). Generic profiles ship
(single, IDEX, toolchanger, MMU) instead of brand names. Capabilities decide the strategy (F5.9).

### F5.3 Part needs: the catalogue

A **need** is something a part asks of the jig. Every need has a short name, a plain-language description, a
**preset** scale for people who want one choice, and parameters for people who want to tune everything. Every
parameter has a default that is right for most parts; `auto` means "derived from the part" (its package tolerance,
its heat, its size).

| Need | Plain meaning | Presets | Main parameters (default) |
|---|---|---|---|
| `flex` | a flexible liner forms around the part, for parts whose size varies or that stick out more than their 3D model | `soft`, `medium` (default), `firm` | `tolerance_mm` (auto from F5.5), `squeeze_mm` (0.15), `shore` (from preset: soft 85A or TPU 95A at 30 % gyroid, medium 95A solid, firm 95A + rigid ribs), `thickness_mm` (auto: 3 x (tolerance + squeeze), 1.2..3.0), `coverage` (`floor`, `walls`, `top`, `pins`; default floor + walls), `zones` (`all`, `ends`, `pins`, or rectangles in part coordinates), `pattern` (`solid`, `gyroid:N%`, `ribs:W/G`, `honeycomb:N%`), `pin_tolerance_mm` (extra soft column under single pins that stick out, e.g. a shield or ground pin; auto for shell pads detected by `heat.SHELL_PAD`), `retain` (`none`, `light`, `firm`: an undercut lip in the liner) |
| `heat` | the jig survives soldering heat at this part | `warm` (100 °C), `hot` (150 °C, default for hot parts), `very_hot` (230 °C) | `max_temp_c`, `duration_s` (auto from joint count x 4 s), `method` (`material`: a zone in a material with `hdt_c` at least `max_temp_c` + 20; `insert`: room for silicone, PTFE or FR-4 as today's `heat_insert_mm`; `gap`: an air gap with ribs; `sink`: a pocket for a metal block), `zone_mm` (3 around the hot surfaces) |
| `sturdy` | this area takes load or wear | `normal`, `strong`, `very_strong` | `zone` (`hinge`, `latch`, `posts`, `frame`, `pocket`), `material` (auto: the stiffest on hand, PA-CF / PETG-CF), `walls`, `infill_pct` |
| `esd` | contact surfaces dissipate static | `on` | `resistivity_ohm` (1e6..1e9), `ground_stud` (a pocket for a ground lead), `zones` (contact surfaces only, default) |
| `cushion` | a fragile part is held gently (glass diodes, crystals, ceramics, displays, optics, large MLCCs) | `gentle`, `very_gentle` | `max_pressure_kpa` (50), `material` (auto: the softest on hand), `thickness_mm` |
| `retain` | the part must not fall out when the stack is turned over | `light`, `firm` | `method` (`lip`, `friction`: a slight interference in a flexible liner, `clip`), `force_n` |
| `support_leads` | long or thin leads that bend get a comb that keeps them straight | `on` | `pitch_mm` (from the footprint), `depth_mm` |
| `keepout` | surfaces nothing may touch (optical windows, buttons, labels, membranes) | `on` | `faces` (`top`, `sides`, rectangles), `margin_mm` (0.5) |
| `polarity_key` | the pocket fits one orientation only (poka-yoke) | `on` (default for polarised parts with symmetric bodies, as a suggestion) | `feature` (`notch`, `chamfer`, `pin1_post`) |
| `standoff` | the part must sit at a set height above the board (LEDs, displays, some sensors) | `on` | `height_mm`, `tolerance_mm` |
| `see_through` | a window to check seating (clear material or an opening) | `on` | `material` (clear PETG), `size_mm` |
| `label` | embossed reference, polarity or pin 1 mark, in a contrasting material when available | `on` (default off) | `text` (auto: reference), `height_mm` |
| `insert` | a bought insert: heat-set nut, magnet, steel pin, weight | `nut_m3`, `magnet_6x3`, `pin_3mm`, `weight` | position, size |
| `chemical` | resists flux and IPA at this part (cleaning in place) | `on` | `agents` |
| `vent` | air can flow past a hot part | `on` | `open_area_pct` |
| `custom` | a region of your own in a material of your own | | `region` (rectangles or a part), `material`, `z_range_mm` |

**How needs are written** (`pcbtestkit.json`, the KiCad dialog and MCP write the same thing):

```json
"jig": {
  "materials": {"rigid": "petg", "flexible": "tpu-95a", "heat": "asa", "esd": "esd-petg"},
  "needs_auto": "suggest",
  "needs": {
    "J1":   {"flex": "medium", "heat": "hot"},
    "C1*":  {"flex": {"tolerance_mm": 0.6, "shore": "90A", "coverage": ["walls"]}},
    "Y1":   {"cushion": "gentle"},
    "D3":   {"keepout": {"faces": ["top"]}},
    "U*":   {"esd": "on"},
    "*":    {"polarity_key": "auto"}
  }
}
```

A need is a preset name, `true` (the default preset), `false` / `"off"` (switched off even if suggested), or an
object of parameters (unset ones keep their defaults). Keys are references, values or footprint names with
wildcards, as in `jig.ignore`; the most specific key wins, then the later one.

### F5.4 Precedence and conflicts

Needs combine per part and per region of the jig. When two needs ask different materials for the same cells:
`keepout` > `heat` > `cushion` > `flex` > `retain` > `esd` > `sturdy` > `label`. Known conflicts get a resolution
and a note, never a silent loss:

- `flex` + `heat` on the same part: flexible filaments soften at 60..80 °C. Resolution, in order: a heat-rated
  flexible material if on hand; flexible liner on the walls away from the hot pins plus a heat insert or heat
  material at the hot pins; a cast silicone liner (F5.9). The guide says which.
- `esd` + `flex`: an ESD-grade flexible material if on hand, else the flexible liner with an ESD rigid rim that
  touches the part first.
- `cushion` + `retain`: retention by a lip in the soft material only.

### F5.5 Detection: the toolkit suggests the needs

Rules are data (`pcbtestkit/needs/rules.json`) with test vectors. Each rule matches on footprint library and name,
value, MPN fields, part category (`classify`), pad types (`heat.SHELL_PAD`), 3D model source (a real model or a
box stand-in), heat (`heat.py`), size and height, and gives needs with a confidence and a reason that the guide
shows. Initial rules:

| Detected | Suggests | Why |
|---|---|---|
| radial and axial electrolytics, film capacitors, inductors with wound bodies | `flex: medium`, tolerance from the package table | diameters vary by up to ±0.5 mm between makers |
| connectors with a metal shell or shield pins (USB, RJ45, D-sub, jacks) | `flex` with `pin_tolerance_mm` at the shield pins, plus `heat: hot` when `heat.py` flags it | shield and ground lugs often stand further out than the 3D model; heavy ground joints heat the shell |
| pin headers, terminal blocks, relays, transformers | `flex: firm` on the walls | body tolerance ±0.25..1.0 mm |
| parts with only a box stand-in for a 3D model | `flex: medium` and a finding to add a real model | the real shape is unknown |
| TO-220/TO-247 and other tab packages, hot parts from `heat.py` | `heat` with the method chosen by printer and inventory | the tab gets hot |
| glass-body diodes, crystals, ceramic resonators, displays, optics, large MLCCs | `cushion: gentle` | fragile |
| tall or heavy parts (height > 15 mm, or mass from a field) | `retain: light` | they fall out when turned over |
| MOSFETs, RF parts, bare sensors (by category), when `needs_esd: auto` | `esd: on` (suggested, never applied without acceptance) | static sensitive |
| polarised parts with symmetric bodies | `polarity_key` (suggested) | fits the wrong way round otherwise |
| long thin leads (axial, LEDs) | `support_leads` | leads bend |
| parts that E3 shows loose all round | `flex` | a liner takes up the gap |

`jig.needs_auto`: `suggest` (default: suggestions are shown, the jig is unchanged until accepted), `apply`
(suggestions are used unless switched off), `off`. Package tolerances come from `pcbtestkit/needs/tolerances.json`
(package family to `{d_mm, h_mm, pin_mm}` ranges), with a `verified` date per entry.

**Where suggestions show:** the report's findings ("J1: consider a flexible liner, the shield pins vary"), the
guide's jig section, `get_open_decisions` (as decisions with `example_args`), and a column in the KiCad dialog.
Accepting is one click, one CLI call or one MCP call; the choice is stored in `jig.needs`.

### F5.6 Geometry: layered heightmaps

The jigs are heightmaps today (one height per cell, meshed by greedy rectangles). Multi-material needs several
materials stacked in a cell, so each cell becomes a short list of **intervals** `[(z0, z1, material)]` (a layered
heightmap). It keeps everything that makes today's mesher fast and watertight:

- Each material's body is the union of its intervals; the mesher runs per material on the interval lists (greedy
  boxes extended to intervals), giving one watertight body per material that touches the others exactly (shared
  faces, no gaps, no overlap). `mesh_check` runs per body plus an overlap check.
- Single-material jigs are the special case of one interval per cell, so 1.2.0 output stays identical.
- OpenSCAD output gets one module per material.

### F5.7 Structure: weaving soft into hard

Soft material must never be a loose island glued on by a thin skin. The builder adds interlocks, chosen per
material pair from `bonds_with` and the zone's shape:

| Interlock | Description | Use |
|---|---|---|
| dovetail rails | the soft liner sits in dovetail grooves in the rigid pocket wall | walls of `flex` pockets |
| mushroom anchors | the soft material goes through holes in the rigid floor and spreads under it | floors of `flex` and `cushion` pockets |
| Z teeth | soft and rigid alternate in a checkerboard every N layers across the interface | wide flat interfaces |
| graded lattice | over `transition_mm` (1.5) a rigid gyroid lattice is filled with the soft material, from 0 to 100 % soft | thick liners, `living` hinges |
| rivets | soft pins through the rigid body, capped both sides | thin parts, poor bonding pairs |

Rules checked on every build (failures are errors, the jig is not written):

- the rigid body stays one connected piece (flood fill on the layered grid) after the soft zones are cut out;
- every soft island has at least two interlocks and an interlock area of at least `min_anchor_ratio` (0.3) of its
  interface area; pairs that bond `poor` need mechanical interlocks only;
- minimum feature size per material: two nozzle widths (`2 x printer.nozzle_mm`), rigid ribs at least 1.2 mm;
- no unsupported soft overhang beyond 45 degrees in the print orientation;
- heat: no material with `hdt_c` below a zone's `max_temp_c` + 20 within `zone_mm` of a hot surface;
- the soft fraction of the frame and of the hinge and latch zones stays below `max_soft_fraction` (0.15) unless the
  zone is a `living` hinge.

The guide gets a short "Why it holds together" section: the interlocks used and the checks passed.

### F5.8 Outputs

- `<board>-jig.3mf` and `<board>-jig-placement.3mf`: every body as its own object with its material and a
  suggested tool number, in one build plate; readable by the common slicers. Written with `zipfile` +
  `xml.etree` (3MF core spec, the materials extension for names and colours).
- `<board>-jig-<material>.stl` per body, for slicers without 3MF.
- `<board>-jig-materials.json`: bodies, grams, volumes, per-body print hints (walls, infill, speed for flexible
  materials), purge estimate for single-nozzle changers, the needs that put each body there.
- Guide: a materials table (material, grams, cost from E6, what it does), a render of the jig in material colours,
  print steps per printer type, and the assembly steps for inserts when the fallback is used.
- Report: needs accepted, suggested and switched off, with reasons.
- Video: the jigs render in their material colours; soft liners compress visibly when the jig closes (with E3).

### F5.9 Strategies for every printer (`jig.multi_material.strategy`)

| Strategy | Printer | What you get |
|---|---|---|
| `multi_tool` | IDEX, tool changer, MMU | one print with every material |
| `inserts` | any | the rigid jig with dovetail slots, the soft liners as separate prints that press in |
| `cast` | any | the rigid jig plus a printed mould for each liner; pour silicone (Shore 20A..60A) and insert |
| `cut` | any | templates (SVG, 1:1) to cut sheet material: PTFE, silicone, cork, EVA for heat and cushion pads |
| `single` | any | one material: needs are met by geometry only (looser pockets, bigger heat room), and the guide lists what is lost |
| `auto` (default) | | the best the printer and inventory allow, in the order above |

Single-nozzle MMUs purge on every change: the builder groups soft zones into as few layer ranges as possible and
reports the purge grams (E6).

### F5.10 Where you set it

- **KiCad dialog**, Jig tab, new "Materials and part needs" section: the printer profile and the materials on
  hand; a table with one row per held part (reference, value, suggested needs as chips, accepted or not), a preset
  per need, and an "Advanced" button per row that opens every parameter with its default shown greyed. Filters:
  "suggested only", "hot parts", "loose parts" (from E3).
- **CLI:** `pcbtestkit jig needs BOARD [--suggested]`, `pcbtestkit jig needs BOARD --set J1 flex=medium heat=hot`,
  `--clear J1 flex`, `--accept-all`; `pcbtestkit materials list|show ID|validate`; `pcbtestkit printers list`;
  `--printer ID` on `run`.
- **MCP:** `get_jig_needs` (R, compact rows `[ref, need, state(suggested|accepted|off), preset, confidence,
  reason]`), `set_jig_needs` (W, batch up to 200 parts), `list_materials` (R), `set_printer` (W);
  `get_schema('jig_needs')` returns every need with its presets, parameters, ranges and defaults.

### F5.11 Defaults that are good for most parts

The defaults are chosen so that `flex: medium` alone works for nearly every part with a dimensional variation:
TPU 95A (the most printable flexible filament), solid, 0.15 mm squeeze, thickness from the part's tolerance
(1.2..3.0 mm), floor and walls, dovetail rails on the walls and mushroom anchors in the floor. `soft` uses the
same filament at 30 % gyroid (about the feel of 70A) so it prints on the same printer; `firm` adds rigid ribs
inside the liner. Users who want more change single parameters; everything else stays at its default.

### F5.12 Calibration

`pcbtestkit jig coupons --printer ID` (A1) writes small test prints: a squeeze coupon per material pair (liners
of 0.1 / 0.15 / 0.2 / 0.3 mm squeeze on a dummy part), an interlock pull test, and a Shore sampler (solid, 50 %,
30 % gyroid). The measured best values go into `printer.calibration` and override the defaults for that printer.

### Acceptance (E5)

- A board with a radial electrolytic, a USB connector with shield pins, a glass diode and a TO-220 (a new
  `examples/make_sample.py` variant) gets exactly the suggestions in F5.5, none applied with `needs_auto: suggest`.
- Accepting all on a two-tool printer gives a 3MF whose bodies are watertight, do not overlap, touch along every
  interface, and pass every rule in F5.7. The same board on a single-material printer gives the `inserts` jig and
  liners, and the guide lists the steps.
- `jig.needs` empty and `needs_auto: off` gives jigs identical to 1.2.0.
- Every material, printer, tolerance and rule file validates; a broken one fails CI with the file and field named.
- A printed multi-material jig (manual test) holds an electrolytic of the nominal diameter and of +0.5 mm with
  neither rattling nor being forced.

## E6 Cost of every build, and downgrading to a budget

**Problem.** The toolkit already prices environment upgrades with rough list prices (`costs` in the environment
spec, `upgrades.py`). It does not say what a single board's kit costs (jigs, fixture, pins, clamp), nor what a
whole catalog costs, and there is no way back when the result is too expensive.

**Goal.** Every output states what it costs to make, as a range, from data you can change. A catalog run prices the
whole catalog including its test environment. When that is too much, the toolkit proposes downgrades whose savings
are larger than what they cost you in tested boards, and you decide which to take.

### F6.1 What is priced

| Item | How |
|---|---|
| 3D-printed parts (jigs, liners, nests, press plates, clamp adapters, moulds) | volume per body from the (layered) heightmaps, times density and an infill/wall factor; grams times `price_per_kg` per material; print time from volume over the material's flow plus layer and tool-change overhead; times `machine_rate_per_h` (default 1.5); plus purge grams for single-nozzle changers |
| Fixture PCB | area, layers, class needed (from the class system), quantity and finish against a price table per fab style (`pcbtestkit/pricing/*.json`, setup fee plus area rate, with a `verified` date; rough defaults) |
| Bought parts | pogo pins and receptacles per family (count from the fixture), headers, ADC boards, the runner computer when the board needs its own, toggle clamps, magnets, pins, inserts (E4, E5), wires |
| Station boards and stations | today's `costs` model (station, sockets, ADC groups, supplies, buses, programmers, plate), plus the station PCB from the price table |
| Labour (optional) | fixture assembly (base plus per pin), jig post-processing, insert assembly, at `labour_rate_per_h`; test time per board from `timing.py` at `operator_rate_per_h` |
| Per tested board | one-off costs over the planned volume (`production.volume`, `production.years`) plus test time and consumables |

Every price is a triple `low / typical / high`; totals are ranges. Prices are rough and say so; users set their
own in `pcbtestkit.json` (`costs`), in `settings.json` (for every project) or as a price table file. Currency per
file; no exchange rates are fetched (nothing goes to the network).

### F6.2 Where costs show

- **Guide and report:** a "What it costs" card: one-off total (range), per tested board at the planned volume, and a
  table by item. A board on an environment shows only what is new for it (its fixture, jigs, any programmers to
  buy), with the environment's share listed separately.
- **Station page:** per board type and for the station.
- **Catalog page (`index.html`):** the total for the whole catalog including the environment, a cost column on
  every card and in the ranking (sortable), and a static SVG chart of cost against boards covered for the layouts
  and downgrade steps (no script; a table gives the same numbers).
- **Files:** `costs.json` and `costs.csv` (a purchase list with quantities, A9) next to every output.
- **CLI/MCP:** `pcbtestkit costs BOARD|DIR [--volume N]`; MCP `get_costs` (R, compact).

### F6.3 Downgrading to a budget

The inverse of `upgrades.options`. For a built environment, `upgrades.options(env, direction="down")` lists
single changes that save money, each with its saving and its loss, all estimated from the board profiles (no
fixture built):

- fewer analog input groups, supplies or bus instances on a station (boards that relied on them lose batch size or
  stop fitting);
- a smaller plate (fewer sites);
- capping batches (fewer fixture sites and programmers per board type);
- merging two stations into one, or removing a station (its boards move where they fit);
- a cheaper fixture class or no routing (the fixture then needs work by hand: listed);
- leaving out boards whose marginal cost is higher than their worth (`value_per_board`, priority, batch);
- single-material jigs instead of multi-material ones (E5), separate instead of hinged jigs (E4).

**Ranking.** By saving minus lost worth, so that the first options are those where the cost drops by more than
the loss. Every option lists what you lose in plain words: "boards that no longer fit: 3 (names)", "batch of
sensor_20: 8 to 4", "coverage of X: 64 % to 51 %".

**Paths and goals** (extending `plan_goal`, which today only adds):

- `--budget 2500`: the most worth within the budget (greedy plus local search over the options, as for upgrades);
- `--keep all`: the cheapest environment that still takes every board;
- `--keep BOARD,...`: these boards must stay, everything else may go;
- `--drop-unprofitable`: leave out every board that costs more than it is worth.

Results are a table of steps (cumulative cost, boards kept, worth) and the list of boards left out, each with its
options: test it by hand, a separate cheap fixture of its own (priced), or the dedicated tester `value_per_board`
stands for. **Nothing is applied without you:** `pcbtestkit environment downgrade DIR --budget 2500` shows the
plan; `--apply` builds the downgraded environment into a new folder (`<name>-rev<N>`) and registers it (E1), so
the old one stays until you forget it. Removing pins breaks the pin-stable promise of upgrades: the plan lists
every fixture that must be rebuilt.

MCP: `plan_environment_upgrade` gains `direction: "down"` and `budget`; `upgrade_environment` applies a downgrade
plan the same way (background job). The KiCad dialog for many boards gets a "Fit to budget" field next to the
upgrade options.

### Acceptance (E6)

- The sample board's kit cost equals a hand calculation from the test price tables within rounding.
- On the 128-board example catalog, `--budget` at half the current cost gives a plan whose worth per euro is not
  worse than removing stations one by one (property test), and every board left out is named.
- With `--apply`, the old environment folder is untouched and the new one builds and registers.
- Every page shows ranges, the currency and the date the price tables were checked.

## Additions (A)

Features not in the request that the epics above need or that make them much better.

- **A1. Printer calibration coupons.** `pcbtestkit jig coupons` writes small prints to measure a printer's real
  fits: sliding fit (E2 lip and pins), hinge clearance (E4), squeeze per material pair (E5), interlock pull test,
  snap latch force. Results go into `printer.calibration` and replace the defaults for that printer.
- **A2. Bed packing.** Arrange every printable part of a build (both jigs, liners, nests, press plates, clamp
  adapters, moulds) on as few printer beds as possible, per material set; write one 3MF per bed with its print time
  and grams. The guide lists the beds.
- **A3. Engraving.** Board name, revision, jig role (P / H), batch slot numbers, polarity and pin 1 marks embossed
  on the jigs (in a contrasting material when available, E5 `label`), so jigs of different boards are not mixed
  up on the shelf.
- **A4. Analog multiplexers for big boards.** Large boards get very low coverage on a station with few analog
  inputs (the Jetson example: 16 probes, 1.7 % of nets). Optional 8:1 or 16:1 multiplexer boards on the fixture
  scan many nets per input, sequentially; the test plan, runner, timing (scan time) and cost include them.
- **A5. Wear counters.** The runner counts cycles per fixture and jig and warns at the pogo pins' rated life and at
  a jig's expected life (from material and need), with the replacement parts priced (E6).
- **A6. Environment doctor.** `pcbtestkit environment doctor` checks every registered environment: folder present,
  station boards edited since the build, profiles stale, inventory consistent; it never changes anything.
- **A7. Snugness numbers in the fit check.** The per-part gap statistics of E3 also exist without the video, in
  `jig.json` and the report, so agents and CI can check them.
- **A8. Deterministic renders.** Renders that changed by a few pixels make every example regeneration rewrite
  about 50 MB of PNGs in git. Reuse a render when its scene hash is unchanged, and fix the sources of
  non-determinism (ray-tracing seed, timestamps), so regenerations only change what really changed.

## Bugs and maintenance (B)

- **B1. Test suite time.** AGENTS.md says the tests take about 30 s; on a laptop they take about 11 minutes, mostly
  environment builds and station plans in subprocesses. Mark the slow tests (an environment variable selects the
  fast set for local work), keep the full set in CI, and correct the documented time.
- **B2. Release workflow Python.** The release job tests on Python 3.12; CI tests 3.9 and 3.13. Either add 3.12 to
  CI or run the release tests on a version CI covers, so a release cannot fail on a version nothing tested
  (1.1.1 and 1.1.2 failed in the release job).
- **B3. Default branch.** Releases are tagged on the development branch while `main` (the default branch, which the
  repository page and Claude Code plugin installs read) lags behind. Decide the branch model (merge each release
  into `main`, or make the development branch the default) and document it in `docs/PUBLISHING.md`.
- **B4. Repository settings.** Turn on Dependabot alerts and protect `main` (require CI to pass), as the
  publishing checklist says.
- **B5. Example size.** `docs/examples` is about 660 MB on disk. With A8 and the catalog allowlist
  (`docs/examples/environment/.gitignore`) it should not grow per release; consider Git LFS or release assets
  for the videos if it does.
- **B6. Regeneration time.** `tools/regen_examples.py` takes about four to five hours with videos. Parallelise the
  independent examples and reuse unchanged boards (stamps exist for station boards already).

## Appendix A: the request, verbatim

> When we have multiple test environments made already, and we do another board run, the framework should be able to detect what test environments would work best with it, mainly to optimize batch size
>
> The jigs for placement and soldering are also not the same exact size, this is no functional issue but it would be nicer if they are the same size and can slot into eachother, if this does not limit the functionality of the test jigs.
>
> For the jigs' video's I'd like an additional visualizer to show how snug it is, this can be done nicely by making it look like some modeling clay blanket is put on top (for the soldering jig) or below (for the placement jig) and squeezed between the print to show the excess/amount of space between the jigs and the DUT's.
>
> It would also be nice if the 3D printed jigs can have some snug hinge in between them so it becomes one piece that we can fold in. Then another hinged based lock can lock both jigs together like how a briefcase is locked so the turning around step becomes very steady and no shifting around can occur. To limited shifting around we can additionally make the jigs out of multiple materials to allow some softer materials to "form" more around the components, this can be very beneficial for components that might have some dimensional variations (for example a ground pin can be slightly sticking out more then the standard STL shows). This can also help with durabilty and heat transfer. Make sure the framework can detect this properly, but also allow users (either through the UI or CLI or MCP for AI) to select components for specific requirements like the need for other types of filaments to be used (more heat resistant ones, sturdier ones, flexible ones for dimensional variations, etc.). Be sure te be creative as to how much adaptation this component-specific demands can handle, I'd like it to have a load of options with a varying degree of parametrization . The default values for example flexible materials for allowing some deformities should be well enough for most usecases specifically for this unique flexible material option, but then through parallelization the users should be able to finepoint it to their specific needs. Make sure all special component-specific needs for the jigs are very varied, easy to understand while allowing loads of customization. The framework should then be able to take all these component needs into account and create a 3D printable jig where the structural integrity of using multiple materials is assured. For example the softer and flexible tissue needs to be weaved in with the harder filament. I am sure you can make this much more advance then I can describe it so make sure this works super well. Based on these demands the framework should be able to create the multi-material test jigs (of course the users would need slightly more advanced 3D printers to account for multi-material printing, but that is their issue, it is just super nice if we can provide this).
>
> For each and every build we create (jigs, test boards, environment boards, etc.) we should be able to give somewhat of a cost figure. A catalog run can do this for the entire catalog including the test environment. If the user then finds it too expensive, we should be able to downgrade the catalog system so that the cost drops down more then the limitations of this new downgraded catalog system, perhaps this would mean some boards might not be tested with the test environment but that is up to the user to decide whether the cost is what they think they can afford. Just as a kind of goal/target audience indication: This whole cost structure is very important since this while framework is made for people/companies with loads of different products while the individual production demands per board are quite limited. Otherwise they would shift more towards a more expensive test environment that has an entire production facility tailored to it. Or perhaps for smaller companies/electronic production departments that don't have the capital to invest in large production facilities. This side-information is simply as side information and should by no means change this test-kit's code or function
>
> For the multi-material options, the framework should be able to figure out of the boards need this as well and make these suggestions, but the user can overwrite this
